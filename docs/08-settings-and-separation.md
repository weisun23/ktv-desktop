# 设置页、音频分离、在线搜歌调研

**日期**：2026-09-22

## 1. 设置页面

顶栏 ⚙ 打开，分四组：

| 分组 | 设置项 |
|---|---|
| 视频 | 解码方式（自动/硬解/软解）、网络缓冲 |
| 播放 | 默认原伴唱模式 |
| 缓存 | 缓存目录（选择/打开/清空）、下载限速、容量上限、当前占用 |
| 音频分离 | 分离方式（关闭/即时/AI插件）、ffmpeg 状态、分离当前曲目 |

### 硬解/软解为什么需要重建播放器

`--avcodec-hw` 是 **libvlc 实例级**选项，建好实例后改不了。所以切换解码方式时：

```
记录当前播放位置 -> dispose 旧播放器 -> 用新参数建新播放器
-> 重新载入同一片源 -> seek 回原位置
```

用户基本感知不到。网络缓冲同理（也是实例级）。

界面上也说明了使用场景：**硬解省 CPU，但部分老显卡/驱动会花屏或卡顿，此时改软解**。

## 2. 音频分离

### 为什么分两档

| | 即时分离（内置） | AI 分离（插件） |
|---|---|---|
| 原理 | ffmpeg 中置声道消除 | 神经网络（demucs 等） |
| 耗时 | 秒级 | 分钟级 |
| 依赖 | 只需 ffmpeg | PyTorch（约 2.5GB） |
| 质量 | 对人声居中的录音好 | 明显更好 |

本机 **PyTorch / demucs 都没装**，且 Python 3.13 未必有对应 wheel，
所以 AI 分离做成**插件**：不内置模型，只提供调用约定。

```
插件约定：<plugin> --input <file> --output <file>
成功退出码 0，把伴奏写到 --output
```

### 即时分离的原理与验证

```bash
ffmpeg -i in.mp3 -vn -af "pan=stereo|c0=c0-c1|c1=c1-c0" -ac 2 out.mp3
```

人声通常居中（左右相同），左右相减即抵消；侧向分布的乐器保留。

**受控验证**（440Hz 人声居中 / 880Hz 只在左 / 1320Hz 只在右）：

```
原始混合L   人声440=50.0%  伴奏880=50.0%
分离后L     人声440= 0.0%  伴奏880=50.0%  伴奏1320=50.0%
```

人声被完全消除，伴奏完整保留。

**两个坑**：

1. **输出是反相信号**——左右互为相反数。一旦被下混成单声道会整体抵消。
   所以必须以立体声播放（写测试时我一开始用 `-ac 1` 分析，结果全变 0，就是这个原因）。
2. **临时文件必须保留真实扩展名**。`out.wav.part` 会让 ffmpeg 推断不出输出格式，
   要用 `out.part.wav`。

### 局限

- 对"人声不在正中间"的录音效果差（这是中置消除的固有局限，不是实现问题）。
- 只产出伴奏，不产出人声（KTV 只需要伴奏）。
- 目前需要**手动点"分离当前曲目"**，还没做成"播放时自动分离"。

## 3. 在线搜歌：调研结论（未实现）

把三种可能的来源都试了一遍：

| 来源 | 结论 |
|---|---|
| KTV 服务端搜索接口 | ❌ **不存在**。探测 `/music/search.php`、`/music/list.php`、`/music/getlist.php`、`/search.php` 等 6 个路径全部 404；服务端只有 `/i.php`（取 token）和 `/music/do.php`（取流） |
| karaoke-companion 的平台爬虫 | ❌ **已失效** |
| 曲库在线更新 | ✅ 已有（分片下载 manifest） |

### 平台爬虫为什么失效

以 5sing 为例（karaoke-companion 里最小的实现，150 行）：

- **搜索接口还活着**：`POST http://search.5sing.kugou.com/home/json`，能搜到伴奏曲
- **取流接口已改**：老代码调的 `/song/getSongUrl` 对所有 `songType` 都返回
  `{"status":0,"errcode":20010}`
- **新接口加了签名**：用 Playwright 抓真实请求才看到

```
GET /song/getsongurl?appid=2918&clientver=1000&mid=<32hex>&uuid=<32hex>
    &songid=2811197&songtype=bz&version=6.6.72&clienttime=<ms>
    &signature=<md5>
```

  签名算法在 `inf_sign-2.0.0.min.js`（26KB 压缩代码）里，需要逆向。

**结论**：karaoke-companion 的 7 个平台实现（合计 2000+ 行 Java）都已过时，
每个都需要重新逆向签名。这不是"移植一次"的工作量，而是**持续维护**的负担。

### 建议

1. **优先做曲库在线更新**（已有基础）——新歌通过更新 muse.db 进来，
   这是最稳的路径，因为用的是同一个服务、同一套播放链路。
2. 如果一定要接外部平台，建议做成**可插拔 provider**，一次只维护一个，
   并接受"接口变了要跟着改"。
3. 外部平台给的是**普通歌曲**（无原伴唱），刚好可以和第 2 节的音频分离配合：
   搜到歌 -> 下载 -> 即时分离出伴奏 -> 唱。

## 5. 一个工程教训

改 `main.js` 时，我用脚本做了多处替换，其中**有一处锚点没匹配上但没校验**，
结果 `startPlayer` 调用了不存在的 `buildPlayer()`，应用直接起不来——
而冒烟测试因为等不到就绪信号**挂了 7 分钟**才被发现。

教训：**脚本化改代码必须校验替换是否命中**（`assert count == 1`），
否则失败是静默的。后续所有补丁我都加了这个校验。

## 6. 遗留

- 分离没有做成"播放时自动触发"，需要手动点。
- AI 分离只有调用约定，没有实际可用的插件。
- 分离结果不会随缓存清理一起删（伴奏文件和源文件同目录，清缓存会一并删掉）。
- 在线搜歌未实现，见第 3 节的建议。
