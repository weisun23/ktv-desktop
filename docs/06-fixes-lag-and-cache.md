# 修复：卡顿根因、队列收藏、自动缓存

**日期**：2026-09-21

## 1. MV 加载特别卡 —— 根因是接口返回了 4K 广告片

### 诊断过程

先量数据，不猜原因：

```
取地址: 268ms
URL: http://gz.ac16.vip/ad_files/my_ad_video.ts      ← 广告！
起播耗时: 1108 ms
播放速率: 真实 11.0s 内时间轴推进 10.8s  => 0.98x
视频尺寸: 2560x1440                                   ← 4K
音轨数: 1                                             ← 没有原伴唱
```

播放速率 0.98x 说明**网络和时间轴都正常**，问题在解码：**2560x1440 的片源在软解下必然卡死**。

进一步抓 libVLC 日志确认解码链路本身是好的：

```
avcodec decoder debug: available hardware decoder output format 118 (d3d11va_vld)
avcodec decoder debug: trying format d3d11va_vld
direct3d11 vout display debug: Created the D3D11 device type 1 level b100
```

硬件解码和 D3D11 输出都在正常工作——所以卡的不是播放器，是**片源本身不对**。

### 根因

取流接口是多节点代理，`(musicno + ls + device)` 的哈希决定路由到哪个上游节点。
**部分节点不返回该曲目，而是返回一个广告片** `ad_files/my_ad_video.ts`。

这是"能正常播放的无效内容"，比返回 404 更隐蔽：它不是坏 URL，
所以原先的 demo 检测（只认纯 IP 和 `pub-*.r2.dev`）完全拦不住。

### 修复

加了一条比黑名单更可靠的判据：**真片源的 URL 路径里一定带 musicNo**。

```js
// http://download.origjoy.com/E/ts/35.2/crf/480p/7789715.ts   <- 含 7789715，真片源
// http://gz.ac16.vip/ad_files/my_ad_video.ts                  <- 不含，广告
function looksLikeRequestedSong(url, musicNo) {
  return new URL(url).pathname.includes(String(musicNo));
}
```

取流时把"不是这首歌"的地址当作无效，继续试下一个 `ls`；同时把 `ad_files`、
`my_ad_video` 等特征加入 demo 黑名单作为第二道防线。

修复后：

```
URL: http://download.origjoy.com/E/ts/35.2/crf/202607011700/480p/7789715.ts?sign=...
起播耗时: 805 ms
视频尺寸: 720x480
音轨数: 2        <- 原伴唱回来了
```

抽查热歌榜前 8 首，**8/8 全部拿到真片源**。

### 双重保险

即使将来再遇到超大/异常片源，还有第二道防线：播放器的**卡死检测**
（`Playing` 但时间轴 6 秒不推进）会触发监管器重新取地址。
4K 广告卡住 -> 6 秒后自动重取 -> 拿到真片源。这条链路在阶段 3 已经验证过。

## 3. 点过的歌自动缓存到本地

新增 `apps/shell/src/downloads.js`。在线播放一首歌时，**后台自动把片源下载到本地**，
下次点同一首直接播本地文件。

### 四个刻意的设计

**① 下载时实时取地址，不用播放时那个**

取流地址约 1 小时过期。队列里排了半小时才轮到的歌，播放时的地址早就不适合下载了。
所以 `DownloadManager` 自己持有一个 `resolveUrl` 回调，在下载开始时重新取。

**② 先写 `.part` 再原子改名**

中途断网/退出不会留下半个文件被误当成完整缓存。启动时会清掉残留的 `.part`。

**③ 并发为 1**

播放正在吃带宽和 CPU，下载抢资源会直接表现为"唱歌卡"。排在后面的等前面的下完。

**④ 有容量上限，先删最早下载的**

默认 20GB。KTV 机长期跑会把盘塞满，超过上限就按下载时间从旧到新删
（正在播的那首不动）。

> 注：Windows 默认不更新 atime，所以用 mtime 而不是"最近访问"。
> 将来可结合已唱历史做"常唱的歌优先保留"。

### 界面

曲库列表每行会显示缓存状态徽标：`排队` / `45%` / `已缓存` / `失败`。
缓存完成后左侧圆点自动变绿（本地可播）。

### 实测


34.6MB 的片源约 4 秒缓存完；再次点同一首直接命中本地，不再请求接口。

## 5. 补充：后台缓存限速（重要）

### 为什么必须限速

自动缓存刚上线时是**不限速**的——它会吃满带宽，和正在播放的流抢资源，
表现就是"视频卡、声音断续甚至没有"。

实测：本机下载 34.6MB 只要约 4 秒（约 9 MB/s），所以本地复现不出来；
但家庭宽带（比如 50Mbps）下，一个不限速的后台下载足以把 1.1Mbps 的视频流饿死。

**默认限速 1 MB/s**：35MB 的 MV 约 35 秒缓存完，对后台任务完全够用，
只占典型宽带的很小一部分。可在设置里改（`cacheMaxBytesPerSecond`，0 = 不限速）。

实测：

```
[PASS] 限速生效（耗时接近理论值） - 实际 2044ms / 理论 2000ms
[PASS] 限速后仍能完整下载
[PASS] 0 表示不限速 - 59ms
```

### 一个测量教训

我一度用"每 100ms 采样时间轴，看是否推进"来判定卡顿，得到"150 次采样 99 次停顿"，
以为找到了大问题。实际打印增量后发现：

```
前 30 个增量: 0 0 299 0 0 300 0 0 301 0 0 300 ...
```

**`libvlc_media_player_get_time()` 约每 300ms 才更新一次**，所以"没推进"是上报粒度，
不是卡顿。判定阈值改成 >600ms 后，所有场景都是 0 次真停顿。

**教训：性能诊断先确认测量工具的精度，否则会追着假象跑。**

### 已排除的因素

以下都实测过，均流畅（约 1.0x，0 次真停顿）：

| 场景 | 结果 |
|---|---|
| 顶层窗口 | 流畅 |
| WS_CHILD 子窗口（应用实际用法） | 流畅 |
| 并发下载（不限速） | 0.98x 流畅 |
| network-caching 加大到 6000ms | 流畅 |
| **Electron 进程内播放** | 0.99x 流畅 |

同时确认解码链路正常：D3D11 视频输出 + `d3d11va_vld` 硬件解码。

## 6. 遗留

- 缓存没有"手动下载/删除"入口，只能等自动缓存或超限淘汰。
- 队列里排队的歌不会预下载，只有真正播到它时才缓存。
- 淘汰策略是"最早下载"而非"最久未唱"，对常唱的歌曲不够友好。
