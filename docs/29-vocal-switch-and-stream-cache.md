## 一、切原伴唱会"音频快进" —— 根因是坏时间戳上的 seek

### 现象

点一下「伴唱」或「原唱」，音频不是接着唱，而是**往前跳几秒**。

### 实测

先量"到底跳了多少"（每 100ms 采一次 mpv 的 `time-pos`）：

```
1548:28.38  CLICK  1671:31.54  ...          ← 跳了 +3.16 秒
1559:103.58 CLICK  1680:109.14  2146:117.68 ← 连跳两次，一共 +14.1 秒
```

再量"seek 准不准"（在同一个文件上 seek 到指定位置，看落在哪）：

| seek 目标 | 实际落点 | 偏差 |
|---|---|---|
| 20 s | 24.6 s | **+4.6 s** |
| 60 s | 66.4 s | **+6.4 s** |
| 120 s | 121.7 s | **+1.7 s** |

换 ffmpeg 验证（`-ss` 输入定位 vs `-i` 后定位，取同一时刻的帧比 md5）：

```
t=20    不一致
t=60    不一致
t=120   不一致
```

也就是说**画面内容真的跳了**，不是只有时间戳报错。而且：

- **重封装（`-fflags +genpts -c copy`）修不好**：偏差一模一样。
- **关掉网络缓存修不好**：偏差一模一样。
- **关掉流畅模式修不好**：偏差一模一样。

结论：这是**片源自己的时间戳坏了**（`docs/16` 里查过，maidong 的 `.ts` 每隔约 524KB 就有一段数据被整体破坏），
ffmpeg 的 mpegts 解复用器建立不出正确的"时间 ↔ 字节位置"映射，所以**在这类文件上 seek 本身就是不可靠的**。

### 那为什么以前能用？

因为以前**每次切原伴唱都在 seek**：老做法是"换文件 + seek 回原位置"
（`switchSource`），另外 mpv 换音轨后也补了一次 seek
（`_applyVocalMode` 里那句"让新音轨立刻从这个点出声"—— 那是 libVLC 的坑，mpv 不需要）。
两个 seek 都落在这堆坏时间戳上，于是每次切换都跳。

### 修法：换源改成"挂外挂音轨 + 切 aid"

mpv 支持把外部文件当音轨挂进来：

```
audio-add <伴奏文件> auto     # 挂上但不选中
set aid <n>                   # 原唱 <-> 伴唱 就是切这一条
```

`aid` 是**热切换**：不 seek、不换文件、不断音、位置纹丝不动。

实测（同一首歌，点「伴唱」前后每 100ms 采一次）：

```
切伴唱: 203.44 CLICK 203.61 203.71 203.81 ... 211.61   ← 完全连续
切原唱: 230.74 CLICK 230.88 230.98 231.08 ...          ← 完全连续
```

对比修之前那两次 +3.16s / +14.1s 的跳变。

实现上注意两点：

1. **`audio-add` 只能挂一次。** `load()` 之后和 mpv 的 `file-loaded` 事件都会触发挂载，
   没有在途保护就会挂出两条一模一样的外挂伴奏（实测 `aid3` 和 `aid4` 都是同一份文件）。
2. **别在切音轨后 seek。** `_applyVocalMode()` 里那个 seek 已经删掉了 —— mpv 的 aid
   切换本来就是无缝的。

老的"换文件"路径保留着，作为 libVLC 内核的回退（`tryHotSwitchVocal()` 返回 false 时走）。

## 二、在线 MV 卡顿 —— 缓冲只有 2 秒

`_ensureProc()` 里原来写的是：

```js
args.push('--cache=yes', '--cache-secs=' + Math.max(1, Math.round(this._networkCachingMs / 1000)));
```

设置里 `networkCachingMs` 默认 1500，于是 **在线 MV 只有 2 秒缓冲**。
网络稍微一抖就是一次 rebuffer —— 用户看到的就是"一卡一卡的"。
（mpv 自己对网络流的默认是 **10 秒**。）

改成：

```js
const secs = Math.max(10, Math.round(this._networkCachingMs / 1000));
args.push('--cache-secs=' + secs, '--demuxer-max-bytes=150MiB');
```

- **去掉 `--cache=yes`**：mpv 默认的 `--cache=auto` 已经是"网络流开缓存、本地文件不开"，
  强制 `yes` 只会给本地文件套一层没用的缓存线程。
- 缓存秒数以 **10 秒为下限**。

实测（1080p 在线 MV）：`demuxer-cache-duration: 10`、`cache-buffering-state: 100`、丢帧 0。

### 马赛克：硬解改回软解

`videoDecoder` 被设成了 `auto` → `--hwdec=auto` → **d3d11va 硬件解码**。
本项目的片源用硬解会出马赛克（`docs/16` 查过：损坏参考帧会把硬件解码器搞坏，
而硬解不做 libavcodec 那样的错误掩盖），在线流遇到坏包时同理。

v2 → v3 的一次性迁移把 `auto` 改回 `software`（显式选了"硬解"的不动）。

## 三、歌词位置 + 底部条

- **画面歌词默认改成"画面底部居中"**（原来是屏幕正中）。
  KTV 的画面本身常带自己的歌词，叠在正中间会挡住人脸。
  设置页可以切回"屏幕正中"。
- **底部 HTML 歌词条强制关掉一次**（v1 → v2 迁移）。
  它和画面里的歌词是**同一句**，上下各显示一遍，用户会以为出了 bug
  （"画面下方的歌词为什么还在"）。真想要两份的可以在设置页手动打开。

## 四、流畅模式默认关

上一轮加的 `--interpolation=yes --video-sync=display-resample` 默认打开了，
这轮改成**默认关**。

原因：`display-resample` 的前提是"显示器刷新率能被准确测出来"，而实测**同一台显示器上**
mpv 报出来的 `display-fps` 一会儿 **74.968**、一会儿 **60** —— 说明 vsync 时钟
（DWM + 虚拟显示器驱动）并不稳定。`display-resample` 会把音视频节奏**锁到这个测出来的时钟**上，
时钟错了就是持续的顿挫和音画漂移，比它想解决的 3:2 抖动更糟。

想要去掉 30fps 片源在 75Hz 屏上的抖动时再手动打开。

## 五、顺带修掉的：搜不到歌时拿到**别人的歌词**

`searchCandidates()` 原来**完全不校验歌名**，只按歌手做了个排序 —— 而网易云的搜索是模糊的：
拿一个根本不存在的歌名去搜，它照样返回一堆无关结果。实测：

```
搜「这首歌肯定不存在zzzqqq123」
  → 世界上不存在的歌 / 或是一首歌 / 存在 / 不存在的情人 / ...
```

第一候选的歌词会被直接拿去用 —— **用户看到的是别人的歌词，而且时间轴还是对的**，
几乎不可能发现。

现在加了标题核对（`titleMatches`）：

- 先 `cleanTitle` 去掉 `(HD)/(Live)/(DJ版)` 这类后缀，再归一化（去空格标点、转小写）
- 完全相同 → 命中
- 包含关系**要求长度占比 ≥ 0.7**（否则「这首歌肯定**存在**zzz…」会命中《存在》）
- 否则按字符相似度 ≥ 0.7

```
阴天(HD) vs 阴天                → 命中
阴天    vs 阴天 (Live)          → 命中
告白气球 vs 告白气球 (Live)      → 命中
这首歌肯定不存在zzzqqq123 vs 存在 → 不命中
稻香    vs 稻香快乐             → 不命中
```

## 六、修复：换片后旧外挂伴奏残留，导致新片源选错 aid

### 现象

全量测试里 Electron 冒烟偶发失败：

```
切伴唱命中音轨 current=3 expect=2
```

单跑冒烟通过，跑完其他测试后失败。排查发现 mpv 的 `track-list` 里同时有：

- 上一首歌通过 `audio-add` 挂上的外挂伴奏；
- 新测试片源自带的两条音频轨。

`loadfile replace` 不保证清掉外挂音轨，于是新片源被误判成三音轨，策略映射和实际 aid 错位。

### 修法

1. `getTracks()` 只返回片源**自带**音轨，排除 `external`；
2. 换片时记录上一首的外挂伴奏 aid，并在 load 前后主动 `audio-remove`；
3. 冒烟测试开始前先快照并清空真实队列，避免主进程自动续播干扰测试片源。

修复后 Electron 冒烟连续 3 次 27/27 通过，完整 `npm test` 也通过。
