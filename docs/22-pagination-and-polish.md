# 22. 分页补齐与界面细节

> 起因是两个问题：「页面样式能不能优化」和「分页是不是没搞」。

## 一、分页到底有没有

**有，但不好找，而且只覆盖了一半。**

| 列表 | 原来的状态 | 现在 |
|---|---|---|
| 热歌榜 / 搜索 / 歌手 / 在线 | 有「更多」按钮，但**藏在工具栏**里，实测很难注意到 | ✅ 列表底部**吸底常驻**的分页条 |
| 本地文件 | 一次扫完，不需要分页 | ✅ 显示「已经到底了」 |
| **已唱 / 收藏 / 歌单** | ❌ **完全没有分页**，一次性渲染全部 | ✅ 每页 50 条 + 加载更多 |

### 分页条为什么改成"吸底"

原来放在工具栏，30 条要滚很久才到底，遥控器场景更不可能去滚。
改成 `position: sticky; bottom: 0` 吸在滚动区底部，**始终可见**：

```
┌────────────────────────────┐
│ ...歌曲列表（可滚动）        │
│  ───────────────────────   │
│   已显示 30 首  [加载更多]   │  ← 吸底，滚动时一直在
└────────────────────────────┘
```

### 顺手修的一个状态 bug

`hasMore` 是**跨标签共享**的状态，切标签时没重置。
结果从热歌榜（有更多）切到「本地文件」（只有 13 首），
照样显示"加载更多" —— 点了什么也不会发生。

修法：`switchTab()` 里先 `hasMore.value = false`，由各自的加载函数再设。

## 二、收藏/歌单的批量查询

做分页时发现 `loadSongs()` 是**逐个 id 调 `songById`**：

```js
for (const id of ids.slice(0, 200)) {
  const s = await bridge.catalog.song(id);   // 200 首 = 200 次往返
}
```

200 次 IPC + 200 次 HTTP + 200 次 SQL 编译。加了批量接口：

```
POST /songs/batch  { "ids": ["...", "..."] }
  -> { songs: [...] }        // 保持传入顺序，查不到的跳过（已下架）
```

- **SQL 层**：一条 `WHERE id IN (...)`；SQLite 变量上限 999，所以按 500 分批
- **返回值保持传入顺序**：调用方是按收藏/歌单的顺序展示的，用 `Map` 回填

实测（30 首）：

| | 耗时 |
|---|---|
| 逐首 `songById` | **21 ms** |
| 批量 `/songs/batch` | **4 ms** |

条数越多差距越大。

## 三、界面细节

### 3.1 底部图例被挤成两行

实测数据：图例容器 **459px**，而内容自然宽度需要 **458px** —— 差 1px，
于是文字被迫折行，「不可播」被拆成「不可 / 播」，整块高度从 29px 涨到 **49px**，
白白吃掉 20px 的列表高度。

原因是我上一轮往提示里加了键盘说明（`↑↓ 选择 · Enter 确认`），把宽度顶爆了。

修法三条：

1. `.legend span { white-space: nowrap; flex: none; }` —— 不许折行
2. 提示缩短成「双击点歌 · 右键更多」，完整说明放 `title`
3. 容器查询：`@container (max-width: 520px)` 时**隐藏提示**，只留三个圆点图例

结果：图例 **49px → 31px**，列表高度 **477px → 518px**。

### 3.2 工具栏变清爽

分页按钮挪走后，工具栏从 59px 降到 36px。
