本轮四件事，前三件都是**已复现的具体 bug**，最后一件事是产品结构上的拆分。

## 一、"播放时鼠标卡到没反应" —— 查了什么、改了什么

### 先量数据（不猜）

| 指标 | 实测 | 结论 |
|---|---|---|
| 主进程 WM_NULL 往返（窗口消息队列） | avg 0.50ms / p99 7.55ms | 主线程没卡 |
| 渲染进程 CDP 往返 | avg 1.49ms / p99 1.96ms | 渲染主线程没卡 |
| 渲染进程 rAF 帧间隔 | avg 12.97ms / max 13.5ms | 合成器没卡（本机 75Hz） |
| 真实鼠标点击 → DOM 变化（端到端） | 19 / 26 / 53 ms | **点击链路是通的** |
| 200 次相对移动的投递 | 收到 199~200 条，gap 与注入一致 | 鼠标消息没丢没积压 |
| `SetCursorPos` + `GetCursorPos` 延迟 | 视频区 0.032ms / 面板 0.017ms | win32k 命中测试不慢 |
| 视频子窗口矩形变化（2 秒） | 0 次 | 没有反复 `SetWindowPos` |
| CPU（播放中） | electron 12.8% + 4.4% + 4.1% + mpv 20%（单核占比） | 没有跑满 |
| 光标可见性（停在视频上 1.8s） | `CURSOR_SHOWING` 一直为真 | mpv 没有把光标藏掉 |

也就是说：**JS 层、输入投递、消息循环全都健康**，卡的不是这些地方。

### 那卡在哪

剩下的只有 **DWM 合成**这一层。而我们的架构恰好踩在一个已知坑上：

> 视频画面是一个**跨进程的原生子窗口**（mpv 画在自己的 HWND 上，`--wid` 挂到 Electron 窗口的
> 子窗口里），它**压在 Chromium 的渲染窗口之上**。
> Chromium 的 `CalculateNativeWinOcclusion` 会周期性问系统"我是不是被别的窗口挡住了"。
> 遇到"别人的子窗口压在我上面"这种它算不准的情况，它会反复改窗口的可见性/节流状态 ——
> 表现就是**窗口发飘、点了没反应**，而 CPU 和主线程都看不出问题。

### 改动

1. **关掉 Chromium 的原生遮挡计算**（`apps/shell/src/main.js` 顶部）：
   ```js
   app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion');
   ```
2. **不让 mpv 碰光标**（`apps/player/src/mpv-player.js`）：加 `--cursor-autohide=no`。
   mpv 默认 `cursor-autohide=1000`，内嵌子窗口里这套隐藏/恢复很容易和系统抢光标。
3. 顺手把主进程那个"视频区双击检测"的轮询保持原样（50ms 两次系统调用，实测开销可忽略）。

> 如果关掉之后还是卡，下一步该量的是 DWM 的呈现队列（`DwmGetCompositionTimingInfo`）和
> GPU 占用，而不是继续在 JS 里找。

## 二、画面歌词：开关切错对象 + 居中 + 滚动

### 三个问题

1. **控制条上的「词」按钮切的是底部那条 HTML 歌词条**，不是画面里的歌词。
   用户按了半天，画面上的字还在。
2. 画面歌词**贴底**（`osd-align-y=bottom`），用户要**居中**。
3. 没有滚动特效。

### 改法：画面歌词全部走 ASS 字幕

原来有两条路：

| 歌词类型 | 原来的实现 | 问题 |
|---|---|---|
| 逐字（yrc） | ASS 卡拉OK字幕，`\k` 逐字上色 | 贴底、不滚动 |
| 逐行（lrc） | mpv `osd-msg1` 一行文字 | 不解析 ASS 覆盖码，做不了滚动/逐字 |

现在**两条路都编成 ASS**（`apps/shell/src/ass-lyrics.js` 的 `buildRollingAss`）：

- `\an5\pos(640,360)` —— **画面正中央**（可切回贴底）
- `\move(cx, cy+dy → cx, cy, 0, 260)` —— 当前行从下方**滑入**
- `\fad(0, 260)` —— 换行时**淡出**，和下一行的滑入叠成"往上滚"的观感
- 下一行用 `KTVDim` 样式**暗色预览**停在下方，轮到它时无缝接手
- 逐字数据仍然编译成 `\k`，跟着唱变绿

⚠️ **一个容易错、错了又看不出来的点**：ASS 的 `\k` 是相对**事件起点**计时的。
滑入事件比歌词实际开始时间早 260ms，卡拉OK就会整体早 260ms —— 画面上完全正常，
只有对着嘴唱才发现"字比声音快"。所以滑入事件开头塞了一个
`{\k26}` + 空格 把这段时间吃掉。

### 开关语义修正

- 控制条「词」按钮 → 切 **`lyricsOnVideo`**（画面里的歌词）
- 底部 HTML 歌词条 → 挪到设置页（默认关，避免同一句歌词上下各一份）
- 设置页新增：**画面歌词位置**（居中/贴底）、**滚动特效**开关

### 顺带修掉两个"歌词不显示"的静默 bug

1. **歌词比播放器先就绪时字幕被丢掉。**
   点歌那一刻渲染进程就去取歌词了，而 mpv 进程是 `load()` 时才拉起来的。
   `setSubtitleFile` 老写法是 `if (!this.ipc) return;` —— 直接丢掉，
   于是**每首歌的第一首永远没有画面歌词**。
   现在"想要哪条字幕"记在 `_subFile` 里，谁就绪谁负责再调一次
   （`_ensureProc` 起来后、`loadfile` 之后、mpv 的 `file-loaded` 事件里）。
2. **换片源（原唱↔伴唱）会把外挂字幕一起丢掉。**
   `loadfile` 会新建播放项，之前 `sub-add` 的字幕不在新项上。
   现在 `load({ keepSubtitles: true })` 保留，并在 `file-loaded` 之后重挂。

回归测试：`apps/player/test/subtitle-attach-test.js`（真起 mpv 进程）。

## 三、"点伴唱怎么给我切歌了" —— 根因是伴奏被截短

### 复现

```
7005500.accomp.ts  accomp=234.611s  src=239.278s  diff=4.667s
7009126.accomp.ts  accomp=258.377s  src=263.568s  diff=5.191s
7427873.accomp.ts  accomp=354.508s  src=361.979s  diff=7.471s
...（本机 7 个伴奏文件，**每一个**都比原片短 4.7~7.5 秒）
```

### 为什么

AI 分离（demucs）产出的伴奏比原片短几秒（它按 7.8 秒一个 segment 处理，
尾部那段会被丢掉）。而 `separator.js` 在把伴奏**合回 MV** 时写的是：

```js
args.push('-map', '0:v:0', '-map', '1:a:0', '-c:v', 'copy', '-shortest');
```

`-shortest` 让 ffmpeg 以**较短的那条（音频）**为准结束封装 ——
于是 **MV 的结尾被整段切掉**，容器时长也跟着变成音频时长。

### 为什么会"切歌"

切到伴唱是 `switchSource()` 换文件播放。如果此时已经唱过伴奏的时长位置
（比如唱到 4:20，而伴奏只有 4:15），mpv **立刻 EOF** →
播放器发 `ended` → 主进程当成"唱完了"→ **直接切下一首**。

### 三处修复

1. **合并时不能再以音频为准**（`separator.js`）：
   ```js
   args.push('-map', '0:v:0', '-map', '1:a:0', '-c:v', 'copy',
     '-af', 'apad', '-shortest');
   ```
   `apad` 把伴奏补成无限长（尾部补静音），此时最短的是**画面**，
   `-shortest` 就以画面为准截断 —— 产物长度 = 原片长度。
   回归测试里 mock 一个"会把音频裁到 3 秒"的插件，断言产物仍是 5010ms（原片长度）。
2. **已经做坏的伴奏要能自愈**（`separator.js` 的 `existingAccompanimentUsable`）：
   判断"已存在"不再只看文件在不在，还比对时长；短超过 1.5 秒就当它不存在，下次分离自动重做。
   ⚠️ 量不出来（文件被占用等）时**保守放行**，不能把用户已经做好的伴奏废掉。
3. **兜底**（`main.js` 的 `switchSource` / `ended` 事件）：
   - seek 位置按目标片源时长**夹一下**，最多只丢最后半秒；
   - 切换片源期间的 `ended` 不当成"唱完"，切换结束后再复核一次状态 ——
     真唱完了补一次收尾，不会让队列卡死。

## 四、MV 的伴奏分离是怎么实现的

（`apps/shell/src/separator.js`）

**统一接口**：`separate(source, { mode, pluginPath })`，三种模式：

| mode | 做什么 | 耗时 |
|---|---|---|
| `off` | 不分离 | — |
| `instant` | ffmpeg `pan=stereo\|c0=c0-c1\|c1=c1-c0` 中置声道消除 | 秒级 |
| `plugin` | 调外部插件（Demucs），AI 分离人声/伴奏 | 分钟级 |

**带画面的 MV 怎么处理**（关键）：分离器只认音频，但产物必须**保留画面**，
所以分三步：

```
1) 从源文件抽出音轨 → <name>.accomp.src.wav   （-vn -map 0:a:N -ac 2 -ar 44100）
2) 交给插件            → <name>.accomp.sep.wav （<plugin> --input src --output out）
3) 把伴奏合回原视频    → <name>.accomp.ts
      -i 原片 -i sep.wav
      -map 0:v:0 -map 1:a:0     # 画面用原片的，音轨用分离出来的
      -c:v copy                 # 画面直接复制，不重编码、不损画质
      -af apad -shortest        # 见上一节：以画面为准截断，长度和原片一致
```

产物命名固定为 `<原名>.accomp.<ext>`（`accompanimentPath()`），
播放时切"伴唱"就是**换文件播放并接上播放位置**（`switchSource`），
而不是切音轨/切声道 —— 因为这类 MV 本身就是单音轨、左右声道也不是原伴唱。

**即时分离**（`instant`）同样保留画面，只是第 2 步换成 ffmpeg 的 `pan` 滤镜，
秒级完成、零依赖，代价是只对"人声在正中间"的录音有效。

**进度与优先级**：插件进程被降到 `BelowNormal`，且全局**串行** ——
两个 demucs 各跑满所有核心会把正在播的视频直接饿死。

## 五、数据源二选一：麦动曲库 / 在线源

### 为什么要拆

- **麦动曲库**：67 万首、歌手/语种/首字母分类齐全，但它的 MV 片源**本身带周期性损坏包**，
  视频会卡（详见 `docs/16`）。
- **在线源**：直接搜网易云/酷我，视频流畅，但冷门歌可能搜不到。

用户要的是"**做得明显一点、二选一、有他就没有他**"，而不是混在一起点错。

### 实现

- 新设置 `sourceMode: 'maidong' | 'online'`（默认 `maidong`）。
- 右侧面板**最上面**放一个两块等宽的切换器，选中的整块高亮
  （麦动=绿色、在线=蓝色），副标题直接写清楚代价：
  「歌最全 · 视频可能卡」/「视频流畅 · 搜歌/MV」。
- 曲库页签**按模式整块换掉**：

  | 模式 | 页签 |
  |---|---|
  | 麦动曲库 | 热歌榜 / 搜索 / 歌手 / 本地文件 |
  | 在线源 | 在线搜索 / 本地文件 |

  切模式时如果当前页签在新模式里不存在，自动落到该模式的默认页。
  在线模式默认选中「搜 MV」（用户切到在线源就是冲着"不卡的 MV"来的）。

「本地文件」两个模式都保留 —— 它和取流来源无关。
